# Track logic and race flow against the original (golden trace)

The golden trace ([golden-trace.md](golden-trace.md)) also compares the race flow and the track logic. The emulator side is `reverse-engineering/emulator/track_trace.py`, the port side `packages/lego-racers/src/modules/golden-trace/controller/track-trace/track-trace.ts`, the suite `track-logic.golden.spec.ts` (`pnpm run golden-trace`).

## What is compared (every frame, bit for bit)

| Field                                                                                      | Original                                                                                                                           |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `track.events.<class>`                                                                     | the twelve event arrays of the event set (`race +0x2098`, arrays `+0x5c..+0x8c`): identifier, state, flags, 2A/4B timer, hold bits |
| `track.hazards`                                                                            | `race +0x2148`: identifier (`+8`) and lifecycle (`+0xc`) of every hazard                                                           |
| `track.surfaces`                                                                           | `race +0x27e0`: the flags (`+8`) of every track-material entry (the barrier hazards set `0x10000` and `0x20000`)                   |
| `track.triggers.main`, `.environment`                                                      | `race +0x2080`, `+0x2128`: touch flags (`+0x38`, bits 0 and 1) and the racer masks (`+0x3c`, `+0x40`)                              |
| `track.timers`, `track.timeList`                                                           | `race +0x213c` timers (`+0x18`, `+0x1c` bit 0) and the registry's time list (`+0x4ac + 0xc`, entries `+0x14`, `+0x18`)             |
| `track.world.<track/blended/local/sky>.materials`, `.skeletons`                            | every material animation entry (flags 2 and 4, time) and every skeleton instance (flags, both clip times, clip, blend, position)   |
| `track.sky`                                                                                | `Sky_Update`'s state: per-setting time and keyframe, previous and current setting, blend duration and time                         |
| `race.finishedCount`, `.isRunning`, `.pauseState`, `.placements`, `.unidentifiedCountdown` | `race +0x3330`, `+0x3334`, `+0x30c0`, `settings +0x15e + 0x5c·i`, `+0x334c`                                                        |
| `racerN.flow.*`                                                                            | lap count (`+0xce0`), lap times (`+0xcec..`), countdowns (`+0xd74..+0xd84`)                                                        |
| `race.phase`, `race.phaseMilliseconds`, `racerN.racer.*`                                   | already compared by the shared runner (state 1 to 5, places, laps, zones, flags)                                                   |

Skeleton instance flag `0x8` (fade distances, `0x10028110`) is masked: the port does not model it.

## Scenarios

`track-logic.golden.spec.ts` runs the **13 tracks** (`RACEC0R0` .. `RACEC3R0`) for 1,500 frames and the **12 mirrored second passes** of circuits c3 to c5 (`isMirrored`) for 600 frames; together the 25 races of `LEGORACE.RCB`. Every racer is a computer (`localPlayerCount` 0, a demonstration race), so no input is needed. `TRACK_TRACE_FRAMES=9000 TRACK_TRACE_RACES=...` runs whole races: the original ends a race after 3,700 to 8,900 frames (all six racers finish and the results state ends the loop).

The suite asserts that every field above matches until the first frame where a racer's physics or the random cursor differs (`race.randomPosition`: the power-ups' oil slicks, cannons and grapples spawn emitters the port does not simulate yet, which draw from the table; the other golden-trace owners fix those). Everything after that frame is a consequence, not a finding.

## Open

- **Hazards do not touch racers.** Traced, not ported: a hazard registers in its **Begin** (vtable `+4`) with `CollisionRegistry_Register` (`0x0042fb50`): entry `{owner = hazard, type, flags 1, 0, 0, shape = hazard + 0x10}`; type 4 for the ghost `0x2b` (`0x0048cac0`), lava `0x2c` (`0x0048d980`), capture `0x48` (`0x0048df20`), rock `0x2e` (`0x0048e4b0`) and crane `0x32` (`0x00490070`), type 3 for the hammer `0x3e` (`0x0048be00`, a box). End (vtable `+8`) sets entry `+0x24` to 0 (inactive). The shape is a `0x00411a40` sphere (vtable `0x004af7cc`): centre at `+4..+0xc`, radius `+0x10`, x extents `+0x14`, `+0x18` (in the hazard: `+0x14..`, `+0x20`, `+0x24`, `+0x28`); the walk is the same as for triggers (`0x0043d270`; flags 1 for every class, so computers and players). The callbacks (vtable `+0`: lava `0x0048dcd0`, capture `0x0048e050`) act on the racer (`racer +0xaa8`, `+0xa00`, `+0xb2c`, the car body's slots). What is missing is each class's **shape position**, which its `Update` takes from a skeleton bone pose (`0x0048da10` lava, `0x0048dfa0` capture): pose sampling exists (`skeletal-animation`) but the bone chains are not wired. Classes in the races: hammer `RACEC0R0`, `RACEC2R2`; crane `RACEC0R1`; lava and rock `RACEC0R3`; ghost `RACEC1R0`; capture `RACEC2R3`; warp pad `RACEC3R0` (already a racer trigger).
- Events 29, 3D, 52 and 53 still see `STATIC_TRACK_WORLD` for sounds and material animations (`getIsAnimationPlaying`, `getIsSoundAvailable`); 3D and 52 follow an object's bone.
- The animation modules (`skeletal-animation`, `world-animation`, `sky`) compute in the race's single precision whatever precision the race is given, so the double-precision scenario of the shared suite differs from frame 4 (the game never runs double).
- Power-up objects (oil slick, cannon, grapple) and the racers' physics after the first contact: see [golden-trace.md](golden-trace.md); the lap times and places differ only after those.
