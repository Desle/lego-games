# Session replay: the player's own races as regression tests

A race of the port is a pure function of its load options, its random cursor and, per frame, the integer frame time and the input state ([golden-trace.md](golden-trace.md) feeds the original the same). The viewer records exactly those, so any session can be replayed later on the port and on the original in the emulator, and the first divergence found.

## Recording (viewer)

- `packages/lego-racers-web/.../race-recording/race-recording.ts`: `createRaceRecording(start, search)` is called when a race starts (`beginRace` in the race controller). It returns `null` in the high-definition view (`?hd`, `getIsHighDefinitionEnabled`) and for a race with a ghost. The race loop calls `addFrame` for every frame it steps and `finish` when the loop ends or the race is left.
- Each frame holds the integer `dt` (the frame clock's), the `RaceInputSnapshot` (pressed `KeyboardEvent.code` values, gamepad axes and buttons), the menu keys and the developer power-up grant, i.e. the arguments of `stepRace`.
- `session-recording-store.ts` keeps the last 20 recordings in IndexedDB (database `lego-racers-recordings`), falling back to memory; every access is in try/catch. It works in production builds, quietly.
- **Download the last one**: F9, or the "Download the last session recording" button of the developer panel (backquote). Both are development only.
- **The inbox (development only).** When a recorded race ends (finish, quit or restart) the viewer POSTs the recording to `/__development/replay-inbox?name=<race>-<time>.replay.jsonl`, a route of the Vite dev server (`replay-inbox-server.ts`, `apply: 'serve'`: no production build has it, and `postRecordingToInbox` returns at once unless `import.meta.env.DEV`). The plugin accepts only `[\w-]+.replay.jsonl` names and bodies whose first line is a header, and writes `reverse-engineering/replays/inbox/<name>` (gitignored; `LEGO_REPLAY_INBOX` moves it). With `?hd` no recording exists, as before. On every dev page load `postUnsentRecordings` posts the recordings still in IndexedDB that an earlier load did not send (the sent names are kept in `localStorage`; a repeated post only rewrites the same file name), so races played before the inbox existed are not lost.

## File format (`*.replay.jsonl`, version 1)

Line 1 is the header (JSON): `raceFolder`, `circuitName`, `racerCodes`, `racerCount`, `localPlayerCount`, `raceModeFlags`, `randomPosition` (the starting random-table cursor), `isMirrored`, `multiplayerLapCount`, `isPointsRecordPresent`, `isCountdownSkipped`, `playerCars` (the builder's answer) and `playerRacers` (the save's racer record, with its car design bytes, for each local player). Every later line is a frame: `[dt, [key codes], gamepad | null, menu | null, grant | null]`. About 30 bytes a frame. Only inputs and settings: no game data, so small files may be committed.

## Replay

`pnpm run replay <file> [--write-expectation]` (needs `original-files/` and the emulator virtualenv, `reverse-engineering/emulator/setup.sh` runs first):

1. **Port**: `replayOnPort` loads the race from the header with the recorded car (`getReplayLoadOptions`) and steps `stepRace` with the recorded inputs; the report gives the final phase and random cursor.
2. **Original**: `getReplayScenario` turns the header and frames into a golden-trace scenario (race session start with those settings, scripted `timeGetTime`, DirectInput scan codes per frame) and `runGoldenTrace` compares every field provider bit for bit, reporting the first divergence (frame, field, both values).
3. The pixel trace of selected frames is not wired in (open).

Run the inbox with `pnpm run replay:inbox [--keep]`: every file of `reverse-engineering/replays/inbox/` is replayed and one line is printed per file (frames compared of the total, the first divergence or "no divergence", why the emulator side stopped early, and the limits that held: controller, gamepad and menu-key frames fed, the car). Processed files move to `inbox/processed/` (`--keep` leaves them). The command also prints the same line for a single file (`pnpm run replay`).

What the emulator is fed (`replay-scenario.ts`), and the limits:

- **Pause-menu keys: fed.** The race's menu handlers (`0x00435c00`, `0x00427810`) take DirectInput key events, so a recorded menu input is tapped as the scan code it stands for (Escape `0x01` pause, `0xc8`/`0xd0` up/down, Enter `0x1c` confirm); a key the held-key feed already presses in that frame is not tapped twice. A gamepad's menu buttons (A, start, d-pad) are the viewer's invention (the original's joystick buttons `0x3000000c..f` only confirm), so they are replayed as the equivalent keys. A frozen race and the menu's answers match bit for bit.
- **Gamepad: fed.** A recording whose gamepad ever steers or presses a bound button (0 to 6) runs the original with the first local player on a joystick slot as `Controls_SetDefaults` (`0x0042e960`) makes it for a gamepad (kind 4, sub type 4, steering axis codes `0x40000001`/`0x40000000`, buttons 0 to 6), and the emulator's DirectInput answers an `EnumDevices` for joysticks with one gamepad whose `GetDeviceState` is the recorded state as a `DIJOYSTATE2` (the stick as an integer in -1000..1000, the range the game sets). The game polls it in its own input manager (`0x0044efc0`). Buttons above 6 are not fed. A keyboard key that drives while the gamepad is the controller stops the feed (the original's controller reads one device; the port reads both); keys in the menu are fed.
- **Finding, fixed in the port:** a gamepad of sub type 4 turns its stick into key events (`0x0044ee40`, `0x0044bb60`): any value below 0 presses axis code `0x40000001` (steer positive), above 0 `0x40000000`, with no dead zone, so the stick steers through the digital bindings and the analog axis is never used. The port's analog steering (an earlier hypothesis) was wrong; `getRacerControls` now quantises the stick to the game's integer range and presses the binding.
- **Finding, open:** after the pause menu closes the original ignores keys that were already down (the menu released the controls and keyboard state is event based); the port reads the held keys again at once. `synthetic-pause-royal-knights.replay.jsonl` pins the first divergence (frame 259, `player0.controller.bindings`).
- **The player's built car: not fed (infeasible here).** The original builds the player's car in `FrontEnd_PrepareRaceSettings` (`0x0042d730`) through `FrontEnd_BuildBuiltCarSlot` (`0x0042dcb0`): from the profile's racer record it makes three model objects with the mesh builder of the live front end object (brick database `MENUDATA\PIECEDB`, `LPieceLo.WDF`, colours, Direct3D), and `RacerSet_SetupRacer` (`0x0043b480`) reads those objects (and a driver figure the port does not port). The emulator stops at the entry of `GameApplication_RunFrontEnd` and starts the race session directly; there is no front end object, selected profile or built slot to call it on, and a stand-in slot with the champion's models would not be the built car. So both sides drive the champion car of the first racer code and the report says so per file (with the recorded chassis and weight); the port's own run of the recorded car is `replayOnPort` without overrides. Closing it needs the emulator to run the real front end to a started race (menu key taps, a save file served from the game folder holding the recorded racer).
- Two or more local players and race mode flags are not fed; a developer power-up grant stops the feed; the emulator has no sound device, so the racing tune's random draw is absent from the comparison (`musicTuneCount: 0`), as in every golden trace.

## Permanent tests

`reverse-engineering/replays/<name>.replay.jsonl` with `<name>.expected.json` (`comparedFrameCount` and the expected first divergence, `null` for none). `pnpm run golden-trace` runs `replay-folder.golden.spec.ts`: each file is replayed and must diverge exactly where its expectation says, so fixing a divergence makes the test fail until the expectation is updated. To keep a session: download it (F9), copy it into the folder, run `pnpm run replay <file> --write-expectation`, commit both.

## Proof

`synthetic-royal-knights.replay.jsonl` (385 frames: the introduction, full throttle, a left turn) was made through the viewer's recorder (`race-recording.spec.ts` drives `createRaceRecording` headlessly with a session on the save's default car). The spec checks that the port replay equals the live headless run field for field, and that the recorder's output equals the committed file. The original in the emulator matches the port bit for bit on all 385 frames (`pnpm run replay`).

`synthetic-gamepad-royal-knights.replay.jsonl` (365 frames: the stick at -0.4237 for 90 frames, then 0.0123, with button 0 held) matches the original bit for bit as a gamepad session. `synthetic-pause-royal-knights.replay.jsonl` (339 frames: throttle, pause, down, up, confirm, steering) matches through the whole menu and diverges at the open finding above. The inbox route is tested end to end by `race-recording.spec.ts` (a race recorded through `createRaceRecording`, posted to a real Vite server running the plugin) and `replay-inbox-server.spec.ts`.
