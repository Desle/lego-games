# Golden trace: the whole race, original against port, frame for frame

The differential tests of [emulator.md](emulator.md) prove each ported function against the original. They cannot see the glue between functions: which input arrives, in what unit, in which order, with which constants and which objects. The golden trace runs the **real race of `LEGORacers.exe` + `GolDP.dll` in the emulator**, the port's `loadRaceDefinition` + `stepRace` beside it, with the same frame times, keys and x87 precision, and compares every observed field bit for bit after every frame.

```
pnpm run golden-trace        # about 2 minutes: 12 scenarios, 6,500 frames of the original and of the port
```

It skips cleanly without the virtualenv or the original files (`LEGORacers.exe`, `GolDP.dll`, `LEGO.JAM` in `original-files/Lego_Racers_Win_Files_EN/Game Files/`). It is **not** part of `pnpm run check` (the specs are named `*.golden.spec.ts`; the default vitest config excludes them, `vitest.golden-trace.config.ts` runs them).

## How the original runs

`reverse-engineering/emulator/` gained a whole-process machine (`machine.py`, `boot.py`, `race_session.py`, `golden_trace.py`; the stubs are `win32_stubs.py`, `crt_stubs.py`, `com_stubs.py`, `com_display.py`):

1. **Boot as Windows would.** `GolDP.dll`'s entry (`DLL_PROCESS_ATTACH`), the exe's static constructors (the `_initterm` tables), then `WinMain` with `-novideo`, stopped at `GameApplication_RunFrontEnd` (`0x0042bdc0`). The window, the Gol device, `GolEntry`, the JAM archive, DirectInput and the display mode are the real game code.
2. **Stubs.** Win32 (files served from the game folder, heaps, TLS, a scripted `timeGetTime` and `Sleep`), the C runtime (`sprintf`, `str*`, `_open`/`_read`, …) on the host, and **fake DirectDraw 4, Direct3D 3, DirectInput 5 objects** whose method tables carry the real argument counts (stdcall cleanup) and answer plausibly: a primary surface with a back buffer, a HAL device with generous caps and four texture formats, one keyboard and one mouse. Callbacks into game code (`DirectDrawEnumerateA`, `EnumDevices`, `EnumTextureFormats`) are generators: a stub yields `(address, arguments)` and gets the callback's return value back. No sound device exists (`DirectSoundCreate` fails), so the original starts no music stream.
3. **The race.** The game settings block (`application +0xabc`) is filled the way the front end fills it (`0x0042d730`: mode 1, race folder, circuit, racer slots with driver codes, local players, the nine keyboard codes copied from the exe's own default table `0x004b0624`), then `RaceSession_Constructor` + `RaceSession_Begin` load everything (`Race_LoadRaceDescription`, `Race_LoadTrackContent`, the load screen included), and the real `Race_RunLoop` (`0x00432540`) runs.
4. **Frames.** `Application_PumpMessagesAndMeasureFrame` (`0x00416ef0`) is hooked: at each call the previous frame is complete, so the harness records its state, queues the keyboard transitions of the next frame as DirectInput events (the exe's own input manager and event queue deliver them to the player controller), and sets `timeGetTime` so the frame gets the chosen integer `dt`. `Sleep` advances the clock, so a `dt` under 12 ms becomes 12, as in the game; the trace reports the `dt` the game really used and the test checks it.
5. **FPU.** The game's own `DDSCL_FPUSETUP` call (`SetCooperativeLevel` flag `0x800`) sets 24-bit precision, as Direct3D does. The control word after the run is `0x7f`: **the race runs in single precision, confirming `RACE_FPU_PRECISION`**. A scenario may force `single` or `double`; the double scenario also matches.

## What is compared

Every frame, for every racer: the physics frame (position, rotation), velocity, world centre of mass, angular velocity and momentum, mass, grounded wheels, contact count, speed, forward speed, throttle, centripetal force, turn radius, yaw rate, flags, travel direction, heading, grip scale and the three scales, the driver (curvature, throttle, flags), the racer (lap, crossings, flags, place, kind, zone history, lap number, power-up chances, checkpoint side, held power-up and its think timers), the four wheels (flags, depth, contact point, anchor, probe segment, ground force, surface values), the display frame and its sphere. For the local player: the controller's bindings, state, boost window, accelerate time and **steering**. For the race: the phase, the phase timer and the random-table cursor `0x004c6ee4`. The racer's collision volume (`racer +0x1c`) is recorded but not compared (below).

The player drives its **champion car** (`isPlayerChampionCar` in `loadRaceDefinition`): a car built from bricks needs the car builder's models, which the emulator's front end does not run. The port holds the introduction on the track world's camera instance ([track-flow-trace.md](track-flow-trace.md)) and has no music stream (`musicTuneCount: 0`), because the original had none.

## Limits of the trace

- **FSIN/FCOS/FSINCOS** run on the host in Unicorn (see emulator.md): a match proves equality with a double-accurate sine, not with the real FPU. `_CIacos` is Python's `acos`; the racer code reads the arc-cosine table instead.
- **No sound device**: the racing tune's random draw does not happen in the original.
- **The champion car** replaces the built car; the car builder is not run.
- **Mirrored races, multiplayer, ghosts, the pause menu and the circuit runner** are not scripted.
- **Computers**, the emitter pools and the route followers are compared too; what still differs is in rows 14 and 15.
- The emulator is slow: about 25 ms per race frame.

## Adding a scenario

Add a `ScenarioCase` to `getCases()`: the race folder and its driver codes (`getCircuitRacerCodes`), a list of `{ milliseconds, scanCodes }` frames (`holdBindings`, `getRouteDrivingFrames`) and the expected first divergence of the player. For a new group of fields, add a reader to `snapshot_fields` in `golden_trace.py` and a provider to `TRACE_FIELD_PROVIDERS` in `port-trace.ts` that returns the same names.
